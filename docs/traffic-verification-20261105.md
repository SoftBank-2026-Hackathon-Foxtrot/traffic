# 실제 트래픽 전환 실험 — 2026-11-05

서울 AWS EC2와 GCP GCE의 testapp을 Cloudflare Tunnel 두 개와 LB로 연결했다.
측정기는 로컬 Python httpx다. README의 k6 스크립트 검증을 대체했다고 주장하지 않는다.
실제 DB·Redis·로그인·WebSocket·서버 종료는 이번 실험에 포함하지 않았다.

## 1. 전환 중 연속 요청

50 RPS 목표로 60초간 요청을 시작했다. 설정 순서는 AWS:GCP 기준
100:0 → 95:5 → 50:50 → 0:100 → rollback(50:50) → 100:0이다.

- 요청 3,000건, 실패 0건. 응답 분포 `{'200:aws': 1654, '200:gcp': 1346}`.
- 전체 p50 79.0ms, p95 110.0ms. 이 수치는 이 실험의 클라이언트 응답 시간이다.
- AWS에서 시작한 30초 요청: HTTP 200, `X-Served-By: aws`. 실험 시작 후 2.99초에 시작해 33.11초에 완료됐다. GCP 100% 설정 성공 후에도 정상 완료됐다.
- 모든 변경·롤백 작업은 실제 Cloudflare PATCH 및 GET 재조회로 SUCCEEDED였다.
- 짧은 구간에서는 이전 대상 응답과 목표 비율 편차가 관측됐다. API SUCCEEDED를 실제 엣지 반영 완료로 사용하면 안 된다.

## 2. 각 비율을 30초간 유지

50 RPS 목표, 각 단계 1,500건. 마지막 10초만 별도로 집계했다.

| 목표 AWS:GCP | 전체 AWS / GCP | 마지막 10초 AWS / GCP | 실패 |
| --- | --- | --- | --- |
| 95:5 | 1446 / 54 | 445 / 54 | 0 |
| 50:50 | 992 / 508 | 193 / 307 | 0 |
| 0:100 | 100 / 1400 | 0 / 499 | 0 |
| 100:0 | 1247 / 253 | 500 / 0 | 0 |

0:100과 100:0의 마지막 10초는 전부 지정한 환경에서 응답했다. 혼합 비율은 짧은 구간에서 목표와 차이가 있어 연결 조건을 추가 비교했다.

## 3. 연결 재사용 여부 비교

설정 재조회 성공 후 30초 대기하고, 연결 재사용 / 매번 새 연결 두 클라이언트를 동시에 실행했다. 각 모드는 25 RPS 목표로 40초, 1,000건이다.

| 목표 AWS:GCP | 연결 모드 | AWS / GCP | 관측 GCP 비율 | 실패 |
| --- | --- | --- | --- | --- |
| 95:5 | keepalive | 1000 / 0 | 0.0% | 0 |
| 95:5 | new_connection | 923 / 77 | 7.7% | 0 |
| 50:50 | keepalive | 742 / 258 | 25.8% | 0 |
| 50:50 | new_connection | 571 / 429 | 42.9% | 0 |

연결 조건에 따른 분포 차이가 관찰됐다. 이 단일 클라이언트 실험만으로 Cloudflare 내부의 선택 단위를 확정하지 않는다.
가중치는 확률적 설정이며, 짧은 요청 집계를 정확한 할당량처럼 해석하지 않는다.
향후 관측에는 목표 가중치와 실제 앱 수신량을 분리하고, 집계 구간·표본 수·측정 위치·연결 조건을 같이 기록한다.
다수 클라이언트·장시간 표본으로 혼합 비율 수렴과 반영 지연을 추가 확인해야 한다.

## 결과와 남은 검증

- 실제 AWS↔GCP 전환·rollback 및 전환 중 긴 HTTP 요청 완료를 확인했다.
- 시험 종료 설정은 AWS 100%, GCP 0%, fallback AWS다. 두 앱과 터널은 모두 실행 중이다.
- HTTP 5xx·연결 오류·타임아웃 발생 수는 이 표본의 결과이며 장기 무중단 보장이 아니다.
- 장애 주입·실제 서버 종료·drain 완료 판정·로그인 세션 유지·DB 컷오버·WebSocket은 미검증이다.
- Alloy·Prometheus·Grafana는 아직 배포하지 않았다. API 결과의 `traffic_verified=false`도 유지한다.
